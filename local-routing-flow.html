Claude-GearShift · 本地路由

GearShift 本地路由

dd-switch 把 Claude Code 指向一个本机按需拉起的 cc-switch-proxy 进程。供应商存在 cc-switch 的 SQLite 库里、由配置页维护；这一页画清它的完整生命周期：进程怎么起来、env 快照在什么时候拍、 关闭时按什么顺序还原，以及每一步失败会停在哪里。

形态 子进程 · 非服务 监听 127.0.0.1:9301 状态 ~/.config/dd-switch/ 影响面 9 个 env 键

为什么要有这一跳

请求路径：多出的一跳就是全部改动

直连时 Claude Code 自己打到供应商；开启路由后它只认本机的 127.0.0.1:9301，格式转换、档位映射、上游选择都交给 cc-switch-proxy。 配置里唯一变的就是 ANTHROPIC_BASE_URL 和凭据。

生命周期

从「开启」到「关闭」的每一步

主干是九步一条直线；所有失败都向右退出，失败路径不会留下半开状态： 要么进程没起来过，要么进程被杀掉并保留状态文件供重试。

顺序是刻意的：先还原 settings，再杀进程。反过来做的话， 进程杀掉了但还原失败，Claude Code 就指向一个死端口，而能恢复它的快照还在—— 那是不可自愈的中间态。现在这个顺序下，任何失败都还能再点一次「关闭路由」。

作用面

只动 9 个键，其余原样

快照记录的是「键在不在」+「原来是什么值」，所以还原是精确的： 原本没有的键不会被留下，原本有的值会被放回去。应用只写两个网络分派键 （网关地址 + 占位凭据），模型键由用户在 settings.json 里自己维护。 非 env 字段（theme、permissions、skills…） 从头到尾没进过作用域。

路由写入 · 关闭时还原

  • ANTHROPIC_BASE_URL
  • ANTHROPIC_AUTH_TOKEN

    （仅当原本存在时才写）

完全不动

  • env 中的其他任何键
  • theme
  • permissions
  • statusLine / hooks
  • skills / agents
  • 其余所有非 env 字段

设计取舍

几条不能违反的约束

  • 进程

    不是 systemd 服务。随开随关，关掉就是关掉；代价是不随主机重启恢复—— 重启后再点一次「开启」会复用已有快照重新拉起。

  • 供应商

    上游地址、凭据、接入点节点都存在 cc-switch 的 SQLite 库里，由配置页经 cc-switch-proxy provider … 增删改；开启路由前必须有一个「当前供应商」。

  • 零硬编码

    可执行文件从 PATH（或 DD_SWITCH_ROUTE_PROXY_BIN）解析， 库路径由 DD_SWITCH_ROUTE_DB 给出。源码里不允许出现个人目录， 有回归测试守着这条。

  • 快照优先

    开启时拍快照、应用映射时不重做快照。所以「改模型」永远不会把 路由自己的配置记成「原来的配置」。

  • 并发锁

    开启 / 应用 / 关闭 / 切换配置档共用一把锁串行。路由激活期间 POST /api/switch 直接 409，CLI 脚本也会拒绝执行—— 它们都会破坏快照语义。

  • 凭据

    真实凭据存在 cc-switch 的 SQLite 库里（用户私有）；写进 ~/.claude/settings.json 的只是占位符 PROXY_MANAGED。 所有 API 响应一律脱敏为 ***，也不进日志、不进 config/*.json。

  • 仅本机

    127.0.0.1:9301 只服务本机的 Claude Code。 SSH 管理的远程服务器没有路由入口，也不会被这套流程碰到。
